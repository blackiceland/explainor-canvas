## Финальный сценарий

# This Code Solves Problems We Don't Have

2 главы. 5 битов. ~4–6 минут.

---

## ИНТРО

**Экран:** тёмный фон. Субтитры появляются построчно.

**Закадр:**

EN: The most common mistake in code isn't bugs. It's code that solves problems you don't have.

RU: Самая частая ошибка в коде — не баги. А код, который решает проблемы, которых у тебя нет.

---

## Бит 1. Задача

**Экран:** сплит-скрин. Слева — код. Справа — рука выполняет полный цикл: подъехала, схватила, подняла, перенесла, положила, отпустила. Код и рука синхронны — каждая строка = одно движение.

```java
public void handleCube(Cube cube, Table table) {
    arm.moveTo(cube.position);
    arm.grab(cube);
    arm.lift();
    arm.moveTo(table.position);
    arm.release();
}
```

**Закадр:**

EN: Say you need to write a program for a robot arm. It grabs a cube off a conveyor belt and drops it on a table. Right now, it's simple. The arm, the table, the cube.

RU: Допустим, тебе нужна программа для роборуки. Она берёт куб с конвейера и кладёт на стол. Пока всё просто. Рука, стол, куб.

---

## ГЛАВА 1 — THE LIE BEGINS

## Бит 2. Strategy

**Экран:** код морфится (Medusa). Справа рука делает тот же цикл. В мире ничего не изменилось.

**Закадр:**

EN: If you asked me what my favorite pattern is, I'd say Strategy. It's simple, elegant — it makes choice explicit. And when I was building this arm, that was exactly the idea: make the grab swappable from the start.

RU: Если бы меня спросили, какой мой любимый паттерн, я бы ответил: Strategy. Он простой, элегантный — делает выбор явным. И когда я проектировал эту руку, именно этого я и хотел: сделать хват заменяемым с самого начала.

**Код — интерфейс (появляется коротко, не задерживается):**

```java
public interface GrabStrategy {
    void execute(Cube cube, Gripper gripper);
}
```

**Код — три реализации (показать быстро, подряд, акцент на том, что они по-настоящему разные):**

```java
public class StandardGrab implements GrabStrategy {
    public void execute(Cube cube, Gripper gripper) {
        gripper.approach(cube.position);
        gripper.close(Force.MEDIUM);
    }
}
```

```java
public class SoftGrab implements GrabStrategy {
    public void execute(Cube cube, Gripper gripper) {
        gripper.approachSlowly(cube.position);
        gripper.close(Force.LIGHT);
        gripper.waitForSensor();
        gripper.adjustToFeedback();
    }
}
```

```java
public class FirmGrab implements GrabStrategy {
    public void execute(Cube cube, Gripper gripper) {
        gripper.preAlign(cube);
        gripper.close(Force.MAXIMUM);
        gripper.lockWrist();
    }
}
```

**Код — оркестратор:**

```java
private final GrabStrategy grabStrategy = new StandardGrab();

public void handleCube(Cube cube, Table table) {
    arm.moveTo(cube.position);
    grabStrategy.execute(cube, gripper);
    arm.lift();
    arm.moveTo(table.position);
    arm.release();
}
```

**Закадр:**

EN: Three implementations. Each one genuinely different. And right now only one is real. The other two are a bet on the future. So damn smart, isn't it?

RU: Три реализации. Каждая по-настоящему отличается. И пока реально используется только одна. Остальные две — ставка на будущее. Чертовски умно, правда?

## Бит 3. Реальность

**Экран:** код уходит. Тёмный фон. Субтитр по центру. Справа рука замирает.

**Субтитр:**

New requirement: some cubes are fragile.
Lift slowly. Keep orientation. Release gently.

**Пауза 2 секунды.**

**Закадр:**

EN: And then reality shows up. Not with a new grip. With a rule that touches the lift, the move, and the release. But GrabStrategy is already the place that makes decisions. Not because it's the right place — but because it's already there.

RU: А потом приходит реальность. Не с новым хватом. С правилом, которое затрагивает подъём, перемещение и отпускание. Но GrabStrategy — уже то место, где живут поведенческие решения. Не потому что это правильное место — а потому что оно уже есть.

---

## ГЛАВА 2 — WHEN REALITY ARRIVES

## Бит 4. Цена

**Экран:** рука уходит на задний план или исчезает. Код занимает весь экран. Три реализации показаны одновременно или последовательно. В каждой появляется `return new GrabResult(...)`. Визуально подсветить: три файла тронуты.

**Если рука остаётся:** она делает один медленный цикл с чуть более мягким хватом — единственное реальное изменение в мире. Контраст: мир едва изменился, код — радикально.

**Код — интерфейс изменился:**

```java
public interface GrabStrategy {
    GrabResult execute(Cube cube, Gripper gripper);
}
```

**Код — StandardGrab (не имеет отношения к хрупкости, но тоже изменился):**

```java
public class StandardGrab implements GrabStrategy {
    public GrabResult execute(Cube cube, Gripper gripper) {
        gripper.approach(cube.position);
        gripper.close(Force.MEDIUM);
        return new GrabResult(LiftSpeed.NORMAL, Orientation.ANY, ReleaseMode.STANDARD);
    }
}
```

**Код — SoftGrab:**

```java
public class SoftGrab implements GrabStrategy {
    public GrabResult execute(Cube cube, Gripper gripper) {
        gripper.approachSlowly(cube.position);
        gripper.close(Force.LIGHT);
        gripper.waitForSensor();
        gripper.adjustToFeedback();
        return new GrabResult(LiftSpeed.SLOW, cube.orientation(), ReleaseMode.GENTLE);
    }
}
```

**Код — FirmGrab:**

```java
public class FirmGrab implements GrabStrategy {
    public GrabResult execute(Cube cube, Gripper gripper) {
        gripper.preAlign(cube);
        gripper.close(Force.MAXIMUM);
        gripper.lockWrist();
        return new GrabResult(LiftSpeed.NORMAL, Orientation.ANY, ReleaseMode.STANDARD);
    }
}
```

**Код — оркестратор:**

```java
public void handleCube(Cube cube, Table table) {
    arm.moveTo(cube.position);
    GrabResult result = grabStrategy.execute(cube, gripper);
    arm.lift(result.liftSpeed());
    arm.moveTo(table.position, result.orientation());
    arm.release(result.releaseMode());
}
```

**Закадр:**

EN: Three files changed. The requirement was about lifting and releasing. But every change went into grabbing. Strategy promised to localize variation. Instead it multiplied the surface of every future change.

RU: Три файла изменены. Требование было про подъём и отпускание. А каждое изменение пошло в хват. Strategy обещала локализовать вариативность. Вместо этого она умножила поверхность каждого будущего изменения.

---

## Бит 5. Смысл

**Экран:** код исчезает. Возвращается исходная версия. Справа рука спокойно делает свой цикл в последний раз.

```java
public void handleCube(Cube cube, Table table) {
    arm.moveTo(cube.position);
    arm.grab(cube);
    arm.lift();
    arm.moveTo(table.position);
    arm.release();
}
```

**Закадр:**

EN: The problem was never Strategy itself. Strategy is a good pattern. The problem was that we picked the center of the design before we knew where the real variation would come from.

RU: Проблема была не в Strategy. Strategy — хороший паттерн. Проблема в том, что мы выбрали центр дизайна до того, как узнали, откуда придёт настоящая вариативность.

**Экран:** код морфится — не в Strategy, а в то, что было бы естественнее для этой задачи.

```java
public void handleCube(Cube cube, Table table) {
    HandlingProfile profile = HandlingProfile.forCube(cube);

    arm.moveTo(cube.position);
    arm.grab(cube, profile.gripForce());
    arm.lift(profile.liftSpeed());
    arm.moveTo(table.position, profile.orientation());
    arm.release(profile.releaseMode());
}
```

**Закадр:**

EN: When the real variation finally came, it wasn't about how to grab. It was about how to handle the whole thing. One object. One place. No three implementations to maintain. Not because this is the only right answer. But because here, the abstraction matches the actual shape of the problem.

RU: Когда настоящая вариативность пришла, она оказалась не про хват. А про то, как обращаться со всей операцией. Один объект. Одно место. Никаких трёх реализаций. Не потому что это единственно верный ответ. А потому что здесь абстракция совпадает с реальной формой задачи.

**Экран:** тёмный фон. Финальный субтитр.

**Закадр:**

EN: A bad abstraction doesn't start where the code gets longer. It starts where every new change has to go through the wrong door.

RU: Плохая абстракция начинается не там, где код стал длиннее. А там, где каждое новое изменение приходится проталкивать через неправильную дверь.

---

## Что изменилось по сравнению с предыдущей версией

**Конфиг убран.** После бита 4 он был антиклимаксом. Вся сила уже в трёх изменённых файлах.

**Разгон сокращён.** Философия Strategy сжата до двух предложений. Конфликт наступает на третьем бите, не на четвёртом.

**Гравитация проговорена явно.** «Not because it's the right place — but because it's already there.» Это закрывает возражение «нормальный разработчик так бы не сделал».

**HandlingProfile подан осторожно.** «Not because this is the only right answer. But because here, the abstraction matches the actual shape of the problem.» Не серебряная пуля, а более естественный центр для этой конкретной вариативности.

**Рука решена.** Бит 4: рука уходит на задний план или исчезает, код берёт весь экран. Если остаётся — один медленный цикл как контраст. Бит 5: рука возвращается для финала.

**5 битов вместо 7.** Две главы, чистая структура, без провисаний.


# Этот код решает проблемы, которых у нас нет

## Главный тезис

Фраза «этот код решает проблемы, которых у нас нет» описывает особый вид инженерной ошибки: мы платим сложностью **сегодня**, чтобы купить гибкость на **завтра**, но завтра либо не наступает, либо наступает совсем другим. В результате мы добровольно увеличиваем «случайную» (привнесённую нами) сложность системы вместо того, чтобы расплатиться только «существенной» сложностью предметной области. Эту оптику удобно держать в голове через классическое разделение «essence vs. accidents» у entity["people","Фред Брукс","software engineering author"] и его тезис о том, что главные трудности софта — в построении точных абстрактных концептуальных структур, а не в «механике» реализации. citeturn9view1

Дальше появляется связь с другой знаменитой формулой. entity["people","Дональд Кнут","turing award 1974"] предупреждал, что преждевременная оптимизация приводит к ненужной усложнённости и даже «снижает» итоговую эффективность из‑за роста стоимости отладки и сопровождения, поэтому важен не запрет на оптимизацию, а правильный момент и место для неё. citeturn8view3 В нашем случае «преждевременная оптимизация» заменяется на «преждевременную расширяемость»: мы добавляем интерфейсы, уровни, точки расширения, конфиги и «на вырост» архитектуру, хотя фактической вариативности ещё нет.

Этот тезис хорошо усиливается тремя дополнительными линиями мысли. entity["people","Дэвид Парнас","information hiding researcher"] показывает, что хорошая модульность — это не дробление «по шагам алгоритма», а сокрытие проектных решений (information hiding) так, чтобы изменения локализовались; при этом он отдельно демонстрирует, что спецификация, которая раскрывает больше деталей, чем нужно, **без необходимости** ограничивает дальнейшие варианты дизайна. citeturn15view1turn15view0 entity["people","Мартин Фаулер","software engineer thoughtworks"] формулирует YAGNI как отказ от «presumptive features» (предполагаемых фич), подчёркивая не только риск «ошибиться в будущем», но и стоимость отложенной ценности: пока вы строите воображаемое завтра, вы не доставляете реальную пользу сегодня. citeturn19view1 А entity["people","Рич Хики","clojure creator"] напоминает, что человеческая способность удерживать сложность в голове строго ограничена, и что нам приходится выбирать, сколько «мячей» мы жонглируем из‑за самой проблемы, а сколько — из‑за «incidental complexity» (побочной сложности), добавленной инструментами и конструкциями. citeturn22view1turn22view0

Позиция этого эссе проста и жёстка: **абстракции должны быть “заработаны” реальными случаями**, а не «куплены» страхом и фантазией. В противном случае код перестаёт быть отражением действительности и превращается в музей возможных будущих миров, где экспонаты обычно мешают ходить. citeturn15view0turn19view1turn22view0

## Основное эссе

Сказать «код решает проблемы, которых у нас нет» — значит указать на систематическое смещение фокуса: вместо того чтобы снижать когнитивную нагрузку и локализовать изменения, мы строим «машинерию» вокруг будущих сценариев. Часто это выглядит прилично: соблюдены принципы, есть интерфейсы, зависимости «инвертированы», повсюду DI, конфиги вынесены наружу. Но именно поэтому эта ошибка коварна: она маскируется под «профессионализм» — и приобретает культурную легитимность. citeturn16view1turn19view0turn22view0

Чтобы не путать это явление с соседними понятиями, полезно провести границы.

**Overengineering** — самый широкий зонтик: «слишком сложно для задачи». Он описательный и часто субъективный (что одному “over”, другому — “норма”). В нашем эссе речь о более точном механизме: создание инфраструктуры для гипотетической вариативности. citeturn9view1turn22view0

**Преждевременная абстракция** — это шаг «обобщить сейчас», когда у вас нет достаточного количества реальных примеров, чтобы угадать правильную ось обобщения. entity["people","Сэнди Мец","oop design author"] описывает типичный сценарий: сначала «красивая» абстракция снимает дублирование, затем требования чуть расходятся, и в общий код начинают проталкивать параметры и условные ветки, после чего абстракция перестаёт быть абстракцией и становится условным комбайном. citeturn21view0

**Speculative generality** — почти буквальный синоним нашего заголовка, но в терминах «code smells»: код создаётся “just in case”, появляются неиспользуемые классы/методы/параметры, и итог — труднее сопровождать и понимать. Во многих каталогах smells это прямо так и определяется, включая важную оговорку: в **фреймворках** такая «избыточность» может быть оправдана, потому что она нужна пользователям фреймворка, даже если сам фреймворк ею не пользуется. citeturn24view0

**YAGNI** (Extreme Programming) — не «анти‑архитектура», а дисциплина против «presumptive features»: не строить способность системы к будущему поведению до того, как это поведение станет нужным. Важно, что у Фаулера YAGNI — это одновременно разговор о вероятности (мы часто ошибаемся в прогнозах) и о стоимости задержки ценности (пока вы строили будущее, вы не выпустили настоящее). citeturn19view1

**Accidental complexity** у Брукса — это всё, что делает задачу труднее без необходимости именно из природы проблемы. Ключевой мостик: когда мы добавляем абстракции “на вырост” без реального спроса, мы **увеличиваем accidental complexity своими руками**. citeturn9view1

**Architecture astronautics** — культурная форма той же ошибки: уход в сверх‑абстрактные схемы и архитектурные разговоры, которые «звучат умно», но слабо соотносятся с полезной задачей. entity["people","Джоэл Спольски","joel on software author"] высмеивает ситуацию, когда архитектура начинает «решать проблемы, которые интересно решать», а не те, которые реально важны пользователю (его пример с Napster — про то, как можно упустить главное ради “peer‑to‑peer” как религии). citeturn14view0turn14view1

Если собрать это вместе, то «код, решающий проблемы которых нет» — это не просто «слишком сложно». Это **конкретный тип ошибки: спекулятивная вариативность**, которая повышает стоимость понимания и изменений, часто обещая ровно обратное. citeturn24view0turn19view1turn22view1

## Почему умные разработчики делают это

Плохая новость: в это попадают не «плохие разработчики». Хорошая: причины достаточно системны, чтобы их можно было распознать и нейтрализовать.

Первая причина — **страх изменения** как фундаментальная данность. Брукс выделяет changeability как одно из «существенных» свойств софта: успешное ПО неизбежно меняется, потому что меняется культурная и техническая среда вокруг него. citeturn9view1 Если вы внутренне согласны с тезисом «всё будет меняться», то очень легко сделать неверный следующий шаг: «раз всё будет меняться, давайте заранее построим универсальные точки расширения». Но из «изменчивости» не следует «универсальность»: чаще следует **хорошая локализация изменений** (Parnas), а не «плагинная архитектура на всякий случай». citeturn15view1turn15view0

Вторая причина — **мы плохо предсказываем, что действительно будет ценно**. В исследованиях/кейс‑стади про онлайн‑эксперименты entity["company","Microsoft","software company"] есть жёсткая статистика: в опыте компании «только около одной трети идей» улучшают метрики, ради которых их делали; вывод — не надо пытаться «построить оптимальные фичи» через длительное планирование без ранней проверки. citeturn20search0turn20search5 Это важный аргумент против предпосылки «мы примерно знаем будущее»: даже когда люди уверены, реальность часто не подтверждает уверенность.

Третья причина — **социальные стимулы и видимость работы**. Абстракции — заметны; простота — незаметна. На ревью проще похвалить «внедрил Strategy, соблюл OCP», чем признать, что лучшее решение — «оставить прямой код, пока не будет второго кейса». Это особенно верно в культурах, где «архитектура» воспринимается как маркер зрелости, а не как инструмент снижения сложности. Спольски описывает ровно этот социальный механизм: люди начинают увлекаться архитектурой как эстетикой и символическим капиталом — и перестают проверять, даёт ли это пользователю хоть что‑то новое. citeturn14view0

Четвёртая причина — **перенос хороших принципов в неверный контекст**. Например, entity["people","Роберт С. Мартин","clean code author"] в «Clean Architecture» обосновывает идею независимости бизнес‑правил от внешних деталей (UI/DB/фреймворков) и формулирует Dependency Rule как правило направления зависимостей. citeturn16view1 Это может быть чрезвычайно полезно, но в «плохих руках» превращается в ритуал: люди строят 4–6 слоёв «как в книге», даже если проект маленький, изменения локальны, а главный риск не в смене БД, а в том, что никто не понимает, где живёт бизнес‑правило. (И вот это уже как раз «решаем проблему, которой нет»: независимость от внешнего мира становится самоцелью.) citeturn16view1turn22view1

Пятая причина — **ошибка в экономике изменений**. Фаулер прямо описывает типовую мотивацию: люди строят presumptive feature сейчас, потому что кажется, будто «сейчас дешевле». Но он же показывает, что сравнение «дешевле сейчас vs дешевле потом» обязано учитывать: (а) вероятность, что фича окажется ненужной, и (б) цену задержки ценности, потому что вы могли выпустить полезное раньше. citeturn19view1

И наконец — **инерция и sunk cost**. Как только «инфраструктура расширяемости» создана, появляется психологическое давление её оправдать. Мец очень точно описывает, как существующий код «доказывает свою необходимость» просто фактом существования, и чем он сложнее, тем сильнее ощущение, что «нельзя это удалить — наверняка важно». citeturn21view0

## Цена: что именно становится хуже

Самая тонкая ловушка здесь в том, что люди чаще всего думают о цене как о «лишних файлах». Реальная цена глубже: вы меняете **геометрию изменений** и **геометрию понимания**.

Первый счёт — **усиление изменений (change amplification)**. Когда вы заранее вводите дополнительные уровни (интерфейсы, адаптеры, фабрики, конфиги), каждое новое требование получает больше мест, которые надо трогать, даже если требование простое. В терминологии Остерхаута сложность проявляется, среди прочего, как «change amplification» и рост когнитивной нагрузки; его определение сложности как того, что делает систему труднее понимать и менять, ровно про это. citeturn11search0turn11search7

Второй счёт — **когнитивная нагрузка как основной лимит**. Хики в «Simple Made Easy» прямо упирает в ограниченность человеческого внимания и рабочей памяти: мы не можем «становиться сильно умнее», значит, единственный устойчивый способ масштабироваться — упрощать, уменьшая переплетение (entanglement) и «incidental complexity». citeturn22view1turn22view0 Это подтверждается и эмпирическими работами по пониманию кода: например, в fMRI‑исследовании Peitek и соавторов показано, что текстовый размер привлекает внимание, а размер словаря нагружает рабочую память; то есть «лишняя структура и лишние понятия» имеют физиологическую цену. citeturn25view0

Третий счёт — **«ложная гибкость» и неправильные оси вариативности**. Если вы угадали ось — хорошо. Если нет, то вы не просто «зря потратили время»: вы закрепили неправильную модель мира. Мец описывает это как «wrong abstraction»: сначала абстракция кажется универсальной, затем требования расходятся, и общий код начинает ветвиться параметрами и условиями, пока не станет «трудно понять и легко сломать». citeturn21view0 Важно: это не случайная беда — это механика. Преждевременная абстракция редко ломается «сразу», она ломается **ровно тогда**, когда будущее приходит чуть иначе, чем вы его рисовали.

Четвёртый счёт — **рост конфигурационной поверхности и риск отказов**. «Расширяемость» почти всегда означает «больше конфигов». А конфиги — это не нейтрально: в обзоре Xu и Zhou подчёркивается, что конфигурационные ошибки стали одной из доминирующих причин сбоев, что диагностика трудна из‑за огромного пространства ошибок и взаимодействий параметров, а цена выражается не только в простоях, но и в поддержке и администрировании. citeturn8view4 Более того, в работе про latent configuration errors показано, что параметры, которые не используются/не проверяются в нормальной работе, могут «проявляться поздно» (например, в failover/error handling) и приводить к тяжёлым отказам и длительной диагностике. citeturn25view2 Это прямой аргумент против «давайте вынесем всё в конфиг на будущее»: вы увеличиваете поверхность для ошибок, которые проявятся в самый плохой момент.

Пятый счёт — **парадокс “дублирование иногда дешевле”**. В дискуссии о понимании кода есть важный эмпирический нюанс: повторяющиеся конструкции иногда действительно легче понимать, чем «умное» обобщение, потому что повтор снижает необходимость строить сложную ментальную модель абстракции. Например, Feitelson в обзоре обсуждает, что многие метрики сложности игнорируют повторения, хотя повторяемый код может быть легче для понимания, чем предполагается. citeturn25view1 Этот нюанс не оправдывает copy‑paste как стиль, но хорошо объясняет, почему «плоский, прямой» код иногда выигрывает у преждевременного паттерна.

В сумме выходит неприятная мысль: преждевременная «гибкость» часто делает код **менее адаптивным**, потому что адаптивность — это не количество крючков, а способность быстро и безопасно менять систему, сохраняя ментальную модель. citeturn15view1turn22view0turn19view1

## Контраргументы и нюанс

Жёсткая позиция «никогда не проектируй наперёд» была бы просто другой формой догмы. Проблема не в предусмотрительности как таковой, а в **спекуляции без сигнала**.

Первый важный нюанс: **в фреймворках и платформах speculative generality может быть нормой**. Даже каталоги smells делают оговорку: если вы делаете фреймворк, то функции могут быть неиспользуемы внутри него, но нужны потребителям — иначе это не фреймворк. citeturn24view0

Второй нюанс: **инвестиции в дизайн бывают экономически оправданы**, и это не противоречит YAGNI. Фаулер в Design Stamina Hypothesis защищает идею, что дизайн «платится» продуктивностью в будущем: вы можете ускориться сегодня, пренебрегая дизайном, но потом заплатите техническим долгом; он честно называет это гипотезой, но фиксирует наблюдаемую многими динамику. citeturn19view0 Важная связка: «делать дизайн» ≠ «делать универсальные точки расширения». Дизайн может означать **прояснение модели**, **сокрытие решений**, **снижение связности**, **тестируемость**, **понятные границы** — без заранее выдуманной вариативности. citeturn15view1turn16view1

Третий нюанс: **YAGNI безопасен не сам по себе**, а в экосистеме практик. entity["people","Рон Джеффрис","xp cofounder"] подчёркивает, что «строить для сегодня» работает, когда вы держите качество дизайна/кода/тестов высоким и умеете рефакторить; иначе вы действительно рискуете получить «везде по коду» и боль при изменениях. Он же напоминает происхождение YAGNI как реакции entity["people","Кент Бек","extreme programming author"] на «давайте сделаем сложное сейчас, потому что пригодится когда‑нибудь». citeturn13view0turn19view1

Четвёртый нюанс: **иногда будущие требования действительно “известны”**. В вопросе «а если мы знаем, что скоро придёт второй провайдер/регулятор/стандарт?» есть два разных случая:

- вы знаете **форму вариативности** (что именно будет меняться, где граница, какой контракт должен удержаться);
- вы знаете только, что «что‑то поменяется», но не знаете форму.

Первый случай — повод делать **information hiding** и «шов» (seam), а не строить «плагинную архитектуру». Показательный пример у Парнаса: вы не должны раскрывать порядок или формат там, где это не требуется потребителю; это даёт гибкость без спекулятивной универсальности. citeturn15view0turn15view1 Второй случай — как раз то, где абстракция почти всегда оказывается неверной.

Пятый нюанс: **проблема не в интерфейсах, а в “неиспользуемых расширениях”**. Даже Фаулер, говоря о YAGNI, прямо предупреждает: «людей привлекает идея, что сейчас дешевле», но правильная оценка должна учитывать вероятность ненужности и стоимость задержки; иногда разумно сделать минимальный шаг, который почти не добавляет сложности, но снижает риск будущего изменения (например, выбрать структуру данных или формат сообщений так, чтобы его можно было эволюционировать). citeturn19view1turn15view1

Практический вывод нюанса: «не строить будущее» не значит «кодить как попало». Это значит: **строить такую систему, где изменения локализуемы, а точки расширения появляются из повторяющейся реальности, а не из воображения**. citeturn15view1turn21view0turn22view0

## Практические инженерные примеры

Ниже — типичные формы «решаем проблемы, которых у нас нет» в backend/enterprise‑коде. Это не “анти‑паттерны ради мемов”, а механизмы, которые выглядят профессионально и потому легко проходят ревью — до тех пор, пока команда не начинает платить когнитивными процентами. citeturn22view0turn19view1turn21view0

### Внедрение Strategy ради единственного поведения

**Что кажется выгодой.** Разработчик хочет соблюсти open/closed: «добавим новый алгоритм без модификации существующего». Логика опирается на идеалы расширяемости и полиморфизма, которые хорошо описаны у entity["people","Роберт Сесил Мартин","object oriented design author"] в обсуждении принципов расширяемости (OCP) и способов избегать разрастания условных веток. citeturn18view1

**Что становится хуже.** Если вариации нет, то Strategy превращается в лишнюю топологию: интерфейс, реализация, провайдер, wiring, тесты на склейку, иногда конфиг выбора стратегии. Это увеличивает «incidental complexity» и снижает прозрачность поведения: чтобы понять, что происходит, нужно пройти цепочку зависимостей. citeturn22view1turn11search7

**Более зрелая альтернатива.** Держать прямой код (или небольшой `switch`) до появления **второго** реального варианта. Когда второй вариант появляется, абстракция «зарабатывается» и становится яснее, потому что ось вариативности подтверждена реальностью. Это близко к духу YAGNI: сначала реальная необходимость, затем расширение. citeturn19view1turn13view0

### Generic pipeline до появления вариативности

**Что кажется выгодой.** «Соберём обработку запроса как конвейер шагов, чтобы легко добавлять шаги и переиспользовать их». Выглядит как модульность и композиция.

**Что становится хуже.** Появляется инфраструктура оркестрации: контексты, типы шагов, обработка ошибок между шагами, обобщённые интерфейсы, и почти сразу — «универсальный» механизм, который должен покрыть разные будущие сценарии. Реальная бизнес‑логика размазывается по мелким обработчикам, и понимание требует собрать пазл. Это прямое увеличение когнитивной нагрузки и переплетения, о котором говорит Хики (entanglement / complecting). citeturn22view0turn25view0

**Более зрелая альтернатива.** Оставить «линейный» сценарий в одном месте до тех пор, пока не появятся 2–3 различных потока, которые реально требуют переиспользования. А когда появятся — выносить общий фрагмент осмысленно, проверяя, что вы выделяете **общий смысл**, а не «похожие строчки». Это в точности тот момент, где совет Мец про неправильную абстракцию становится практичным: лучше временно терпеть повтор, чем зацементировать неверную модель. citeturn21view0turn25view1

### Сложная конфигурация ради одного фиксированного сценария

**Что кажется выгодой.** «Вынесем всё в YAML/JSON, чтобы можно было менять поведение без релиза».

**Что становится хуже.** Вы увеличиваете площадь возможных ошибок, причём типично — **латентных**: параметры могут не проверяться в нормальном потоке и проявиться в аварийном режиме (failover, error handling), когда цена ошибки максимальна. Это именно тот класс проблем, который выделяют работы про конфигурационные ошибки и latent configuration errors: редкие настройки часто имеют высокую тяжесть и долгую диагностику. citeturn8view4turn25view2

**Более зрелая альтернатива.** Конфиг должен быть (а) минимальным, (б) типизированным/валидируемым и (в) покрытым тестами на ключевые режимы. Если причина внедрения конфиг‑слоя — «вдруг пригодится», это почти всегда сигнал остановиться. citeturn25view2turn8view4

### Проектирование под нескольких провайдеров, когда второго провайдера нет

**Что кажется выгодой.** «Избежим vendor lock‑in: сделаем интерфейс Storage/Payments/Email и реализации под разных поставщиков».

**Что становится хуже.** Если второго провайдера нет годами, система носит на себе «фантомную» архитектуру. Это не только лишние классы: это решения об API, исключениях, ретраях, семантике, которые вы вынуждены выбирать сегодня в вакууме — и с высокой вероятностью выберете так, что будущий провайдер всё равно «не влезет» без костылей. citeturn19view1turn21view0

**Более зрелая альтернатива.** Сделать **узкий адаптер** вокруг текущего провайдера и спрятать детали интеграции (information hiding), не обещая универсальности там, где её ещё нет. Clean‑архитектурная мотивация «бизнес‑правила не должны знать детали внешнего мира» сама по себе разумна, но это не требует заранее проектировать “multi‑provider interface”; чаще достаточно правильно очертить границу и держать её маленькой. citeturn16view1turn15view1

### Service layer, который только прокидывает вызовы

**Что кажется выгодой.** «Архитектура слоёв: Controller → Service → Repository. Так принято».

**Что становится хуже.** Если Service не скрывает проектное решение и не содержит бизнес‑правило, он не уменьшает сложность — он расширяет её поверхность: ещё один файл, ещё один уровень трассировки, ещё одно место, где может начаться «абстракция ради абстракции». На языке Парнаса плохая модульность часто как раз в том, что интерфейсы начинают раскрывать лишнее и связывать модули через детали, которые не должны пересекать границу. citeturn15view0turn15view1

**Более зрелая альтернатива.** Делать слой там, где он действительно **локализует изменение** (например, правила транзакций, оркестрация, инварианты домена), а не там, где он просто «поддерживает форму». citeturn15view1turn22view0

### Event-driven усложнение до реальной необходимости

**Что кажется выгодой.** «Сделаем события, очередь, асинхронность — будет масштабируемо и модно».

**Что становится хуже.** Вы добавляете классическую accidental complexity: eventual consistency, ретраи, дедупликация, идемпотентность, мониторинг, backpressure, сложность дебага. Проблема не в event‑driven как таковом, а в том, что это тяжёлый инструмент. Если он введён без реального давления (нагрузки, независимых команд, требований к изоляции), это буквально «архитектура вместо ценности», о которой язвительно пишет Спольски. citeturn14view0turn9view1

**Более зрелая альтернатива.** Сначала синхронный, прозрачный путь; затем — эволюция, когда появляется реальный сигнал (например, отдельный bounded context/доменная граница, SLA, требование независимого масштабирования). Иначе вы создаёте «состояния и графы» (в смысле Брукса: число состояний растёт нелинейно), не получая ключевой выгоды. citeturn9view1turn22view1

### «Расширяемые» абстракции вокруг стабильных бизнес-правил

**Что кажется выгодой.** «Давайте сделаем rule engine / DSL / плагинные правила, чтобы бизнес мог менять всё сам».

**Что становится хуже.** Если правила по факту стабильны и меняются редко, вы заменяете ясную логику на интерпретатор, конфиг‑семантику и диагностику неполадок «в правилах». Это снова рост конфигурационной и когнитивной поверхности, причём с риском латентных ошибок. citeturn8view4turn25view2

**Более зрелая альтернатива.** Код + тесты + ясное место, где живёт правило (и кто его хозяин). Когда бизнес действительно требует динамики — тогда вы «покупаете» сложность целенаправленно и обеспечиваете наблюдаемость/валидацию (иначе получаете конфигурационный ад, который система исследований конфигураций постоянно фиксирует как тяжёлую проблему). citeturn8view4turn19view1

## Финальный синтез

В сухом остатке «код решает проблемы, которых у нас нет» — это не спор про вкусы, паттерны или “Clean vs. not clean”. Это спор про экономику сложности.

Брукс предупреждает: сложность — сущностное свойство программных систем, растущее нелинейно, и поэтому любые дополнительные источники сложности должны быть особенно тщательно оправданы. citeturn9view1 Кнут показывает общий принцип: преждевременное улучшение несущественного (скорости) часто ухудшает существенное (сопровождаемость), поэтому важны момент и критичность. citeturn8view3 Парнас говорит, что правильная модульность — это скрывать проектные решения и не раскрывать лишнего, чтобы изменения были локальны и не ограничивали будущие варианты. citeturn15view1turn15view0 Фаулер и Jeffries превращают это в практику: не строить «presumptive features», пока они не стали нужны, но делать это безопасно — через качество, тесты и способность к рефакторингу. citeturn19view1turn13view0 Хики добавляет главный психологический аргумент: разработка всегда ограничена человеческой когницией; если вы создаёте систему, которую нельзя держать в голове, вы покупаете будущие ошибки независимо от того, насколько красиво всё «разложено по папкам». citeturn22view1turn25view0

Поэтому зрелая формула звучит так: **сложность должна окупать себя немедленно или иметь доказуемый сигнал окупаемости; абстракции — это не моральная добродетель, а финансовый инструмент с процентной ставкой в виде когнитивной нагрузки**. citeturn19view1turn22view0turn8view4

## Заготовки для сценария

### Десять сильных мыслей

- «Расширяемость» без реального варианта — это не гибкость, а speculative generality: код “на всякий случай” делает систему труднее понимать и сопровождать. citeturn24view0
- Существенная сложность неизбежна, но accidental complexity мы добавляем сами — и именно туда часто попадает преждевременная “навырост” архитектура. citeturn9view1
- Модульность — это не “много модулей”, а сокрытие проектных решений и отказ от раскрытия лишних деталей, которые ограничивают будущее. citeturn15view1turn15view0
- Мы слабее, чем думаем, в предсказании ценности: в опыте Microsoft в экспериментах около одной трети идей улучшали целевые метрики — планирование «идеального будущего» часто проигрывает быстрой проверке. citeturn20search0turn20search5
- У любой «точки расширения» есть цена: её нужно понимать, тестировать, мониторить и поддерживать — иначе это просто новая поверхность поломок. citeturn25view2turn8view4
- Конфиги — не бесплатны: конфигурационные ошибки широко признаны тяжёлой проблемой, а «латентные» параметры могут проявляться поздно и бить больнее всего. citeturn8view4turn25view2
- Неправильная абстракция почти всегда деградирует одинаково: параметры → условные ветки → «универсальный» комбайн → код трудно понять и легко сломать. citeturn21view0
- Иногда дублирование реально дешевле “умного” обобщения, потому что повторение снижает требования к построению общей ментальной модели; это нужно помнить как антидот против рефакторинга «по форме». citeturn25view1turn21view0
- “Архитектурность” может стать самоцелью: когда архитектура решает то, что интересно решать, но не то, что полезно, вы получаете astronautics вместо ценности. citeturn14view0turn14view1
- YAGNI — не про «делать грязно», а про «не строить будущие фичи без нужды», при этом сохраняя дизайн‑качество и способность к эволюции через рефакторинг. citeturn13view0turn19view1

### Пять формулировок для сценария

- «Абстракция без второго примера — это ставка на угадайку, а угадайка плохо масштабируется». citeturn19view1turn21view0
- «Мы не делаем систему гибкой — мы делаем её сложной, надеясь, что сложность когда‑нибудь пригодится». citeturn24view0turn22view1
- «Если будущее не пришло, ваш “плагинный” слой остаётся просто налогом на понимание». citeturn24view0turn25view0
- «Хорошая архитектура — это не количество слоёв, а количество сюрпризов, которых она предотвращает». citeturn22view0turn11search7
- «Сложность должна покупать что‑то реальное. Если она покупает только спокойствие — это очень дорогая терапия». citeturn9view1turn22view1

### Пять углов подачи видео

- «Код как музей будущего»: показать, как “на всякий случай” слои превращают проект в экспозицию неиспользуемых возможностей. citeturn24view0turn19view1
- «Прематюрная оптимизация, но про дизайн»: провести параллель от Кнута к преждевременной расширяемости. citeturn8view3turn19view1
- «Неправильная абстракция как сюжет»: рассказать историю Мец (параметры → условия → ад) как центровую драматургию. citeturn21view0
- «Конфиги — это код, который живёт в худших условиях»: связать “на вырост” конфиг‑слой с исследованиями про ошибки конфигурации и латентные параметры. citeturn8view4turn25view2
- «Архитектурные астронавты сегодня»: показать, как умные слова и “правильные” диаграммы могут отвлечь от полезности. citeturn14view0turn14view1

### Пять сильных контраргументов и ответы

- **«Если не строить заранее, потом будет дорого переделывать».** Ответ: иногда да, но цена должна считаться вместе со стоимостью задержки ценности и вероятностью, что вы ошиблись в будущем; YAGNI именно про эту экономику. citeturn19view1turn20search5
- **«Мы точно знаем: второй провайдер/требование придёт через N месяцев».** Ответ: “точно” часто означает «мы уверены, но форма вариативности не ясна». Минимально разумный шаг — шов/information hiding вокруг интеграции, но не универсальный интерфейс на пустом месте. citeturn15view1turn19view1
- **«Но Clean Architecture даёт независимость от БД и фреймворков».** Ответ: даёт, когда есть реальная потребность в этой независимости и команда платит осознанно; но “независимость ради независимости” превращается в слои‑прокладки и рост когнитивной цены. citeturn16view1turn22view1
- **«Дублирование — зло, надо DRY».** Ответ: DRY — не про одинаковые строки, а про одинаковое знание; а неправильная абстракция может быть хуже небольшой повторяемости, потому что она ломает модель мира. citeturn21view0turn25view1
- **«Без архитектуры всё развалится, нужен дизайн заранее».** Ответ: дизайн действительно важен (design stamina), но дизайн ≠ speculative generality; дизайн чаще про ясные границы, локализацию изменений и тестируемость, чем про точки расширения “на всякий случай”. citeturn19view0turn15view1

### Темы и понятия, которые стоит изучить глубже

- Accidental vs. essential complexity у Брукса и последствия нелинейного роста сложности. citeturn9view1
- Information hiding и критерии хорошей модульности у Парнаса. citeturn15view1turn15view0
- YAGNI, presumptive features и экономика «стоимости задержки ценности» у Фаулера. citeturn19view1
- Связка YAGNI + “Simple Design” и происхождение принципа (Kent Beck / Ron Jeffries). citeturn13view0turn26search1
- Wrong abstraction и механизм деградации абстракций (параметры → условные ветки → нечитабельность). citeturn21view0
- Speculative generality как smell и практическое исключение для фреймворков. citeturn24view0
- “Simple vs. easy”, entanglement/complecting и выбор между problem complexity и incidental complexity у Rich Hickey. citeturn22view0turn22view1
- Исследования про конфигурационные ошибки, “configuration hell” и latent configuration errors. citeturn8view4turn25view2
- Эмпирика про понимание кода и нагрузку на рабочую память (code size, vocabulary size) — как реальную цену «лишних понятий». citeturn25view0
- Design Stamina Hypothesis как аргумент «дизайн важен», но не тождественен «строить будущее наперёд». citeturn19view0


Самая точная мысль во всём чате — не «мы выбрали не ту ось», а то, что ты сам сформулировал в конце: абстракция повлияла на всю архитектуру принимаемых решений. Это глубже, чем просто «преждевременная абстракция». Это про то, как ранний выбор формирует русло для всех последующих решений.
